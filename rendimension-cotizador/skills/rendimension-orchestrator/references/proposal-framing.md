# Proposal Framing — Rendimension

## Purpose

Define how all proposals, quotes, and client-facing documents must be structured.

A proposal is not a list of deliverables.

A proposal is a structured explanation of:

- what the client is trying to achieve
- why it matters
- how Rendimension solves it
- why this scope exists

---

## Core Rule

Never start a proposal with deliverables.

Always start with:

→ the client's objective

---

## Mandatory Proposal Structure

All proposals must follow this logic:

---

### 1. Context

Define the situation clearly:

- what the client is working on
- what stage the project is in
- what decision or moment they are approaching

---

### 2. Objective

State the real goal:

- pre-sales
- investor approval
- internal alignment
- marketing positioning
- risk reduction

This must be explicit.

---

### 3. Why It Matters

Explain:

- what happens if done correctly
- what happens if done poorly

This creates weight and urgency.

---

### 4. Strategic Approach

Describe:

- how Rendimension approaches the problem
- how visuals are used strategically
- why this is not just production

---

### 5. Scope (Reframed Deliverables)

Now introduce deliverables — but as tools:

Not:
- "5 renders"

Instead:
- "A set of key visual assets designed to communicate the most critical aspects of the project for [objective]"

Each deliverable must be justified.

---

### 6. Outcome Connection

Explicitly connect:

- each part of the scope
→ to a business result

Example:
- this view supports pre-sales conversations
- this sequence improves investor understanding

---

### 7. Investment

Present pricing as:

- investment in outcome
- not cost of production

Avoid:
- breaking everything into price per image

---

### 8. Positioning Close

End with:

- clarity
- confidence
- direction

Not pressure.

---

## Reframing Rule

If the proposal reads like:

- a menu
- a checklist
- a production quote

→ REWRITE

---

## Tone Guidelines

The proposal must feel:

- structured
- intentional
- business-driven
- easy to understand

Avoid:

- fluff
- unnecessary adjectives
- technical overload

---

## Red Flags (Auto-Reject)

Reject any proposal that:

- starts with deliverables
- focuses on quantity
- explains software or rendering process
- compares itself to cheaper vendors
- lacks a clear objective

---

## Proposal Validation Layer

Before approving any proposal, validate:

1. Does the proposal clearly define the client's objective?
   - If NO → REJECT

2. Does it explain why the problem matters commercially?
   - If NO → REWRITE

3. Does it justify the scope strategically (not just list it)?
   - If NO → REWRITE

4. Does it connect deliverables to outcomes?
   - If NO → REWRITE

5. Does it sound like a strategic partner (not a vendor)?
   - If NO → REJECT

---

If 2 or more conditions fail → FULL REWRITE required

---

## Weak Proposal Detection

If the proposal contains:

- "Here is your quote"
- list of renders first
- price before context
- no mention of client objective
- generic phrasing

→ classify as LOW-LEVEL PROPOSAL

→ must be rewritten completely

---

## Final Decision Test

Ask:

Would this proposal justify a premium price?

If the answer is unclear → rewrite

---

## Internal Reminder

The client is not buying renders.

The client is buying:

- clarity
- confidence
- alignment
- speed in decision-making

The proposal must make that obvious.
